# 규모 검증

파일을 생성하거나 원본 디스크를 스캔하지 않고 합성 메타데이터 100만 개와 구조화 데이터 10만 개를 SQLite에 준비합니다. 일반 테스트·CI에서는 실행하지 않습니다. 저장 위치는 테스트용 로컬 SSD 폴더를 사용하세요.

```powershell
dotnet run --project tools/FindEverything.ScaleBenchmark -c Release -- --directory C:\Temp\FindEverythingScale --files 1000000 --catalog 100000
```

같은 DB의 조회만 재측정하려면 `--reuse`를 추가합니다. 빠른 개발 확인은 `--files 2000 --catalog 2000`으로 실행할 수 있습니다. 위치를 지정하지 않으면 시스템 임시 폴더 아래에 새 디렉터리를 만듭니다. 준비한 DB는 재측정을 위해 남기며 경로를 출력합니다.

출력은 첫 500행, 검색 20회의 P95, 순차 20페이지, 선택 3개 조회, 구조화 숫자 정렬·필터 개수, 메모리 수치입니다. 구조화 기본 경로 정렬은 오름차순·내림차순의 첫 500행과 **저장된 전체 데이터의 마지막 500행**을 각각 측정합니다(`CatalogPathDeepOffset`이 실제 위치입니다). 숫자·날짜·텍스트 정렬은 처음과 마지막 페이지, 숫자 정렬은 20개 분산 페이지와 전체 선택 내보내기 순회까지 측정합니다. 전체 내보내기 측정은 모든 컬럼을 읽되 CSV/XLSX 파일을 생성하지 않습니다. 출력의 `Environment`에는 빌드된 어셈블리의 commit SHA, OS/runtime/architecture, UTC 시각이 포함됩니다. 미커밋 코드 측정은 실행 전 `FINDEVERYTHING_PERF_WORKTREE=uncommitted`를 명시하세요. SHA만으로 미커밋 변경을 구별할 수 없습니다.

UI 렌더링·스크롤이나 실제 디스크 스캔 시간은 포함하지 않습니다. Windows 11·16GB RAM·로컬 SSD의 앱 실행 검증과 함께 사용하며 다른 OS에서의 결과를 Windows 성능 보장으로 해석하지 않습니다.

## 정렬 페이지와 내보내기 구현

기본 경로순 목록은 기존 projection PK를 사용합니다. 그 외 정렬은 고정된 쿼리마다 한 번만 정렬한 경로 키를 SQLite의 파일 기반 TEMP 테이블에 저장하고, 이후 페이지는 ordinal PK로 바로 접근합니다. 선택 항목 목록도 동일한 선택을 재사용하는 동안 이 순서를 유지하며 선택이 바뀌면 다시 준비합니다. TEMP 페이지 캐시는 2 MiB로 제한하고, 쿼리가 닫히면 SQLite가 임시 파일을 정리합니다. 전체 내보내기는 순서를 한 번 준비한 뒤 기존 8 MiB 단위의 값 읽기 제한을 유지하므로 페이지마다 정렬/OFFSET 탐색을 반복하지 않습니다.

첫 정렬 페이지는 순서 키를 준비하는 비용까지 포함합니다. 따라서 첫 페이지와 재사용한 깊은 페이지를 별도로 비교해야 합니다. 회귀 테스트에서는 실제 깊은 페이지 SQL의 `EXPLAIN QUERY PLAN`에 ordinal `INTEGER PRIMARY KEY` 탐색이 있고 `TEMP B-TREE`가 없는지도 검사합니다. NULL 값은 오름차순·내림차순 모두 마지막이며, 동일 값은 경로순으로 안정화합니다.

WPF UI 측정 JSON은 별도의 Windows smoke fixture에서 생성합니다. 샘플이 0개인 heartbeat 지연은 `null`/`unmeasured`이며, `0 ms`로 해석하지 않습니다. 20개 미만은 `insufficient-samples`로 표시합니다. UI 자료에는 실제 viewport와 DPI도 포함되므로 다른 조건의 숫자를 직접 비교하지 마세요.

## 측정 기록

2026-10-13, macOS / .NET 10.0.12, 파일 메타데이터 1,000,000개와 구조화 항목 100,000개를 준비한 DB의 데이터 계층 측정입니다. 합성 데이터는 짧은 문자열 3개와 숫자·날짜 필드를 사용했습니다. 준비 시간은 메타데이터 약 205.5초, 구조화 약 42.4초이며 아래 조회 시간에 포함하지 않습니다. 이 기준 측정 후 추가된 표시용 텍스트 미리보기와 메모 revision 검사는 별도 회귀 테스트로 확인했습니다.

| 측정 | 시간 |
|---|---:|
| 파일 첫 500행 | 70.2ms |
| 파일 검색 P95, 20개 입력 | 222.6ms |
| 파일 순차 20페이지 | 88.6ms |
| 선택 경로 3개 | 107.7ms |
| 구조화 첫 500행 | 30.0ms |
| 구조화 검색 P95, 20개 입력 | 233.5ms |
| 구조화 숫자 역순 첫 500행 | 81.3ms |
| 구조화 필터 개수 | 113.6ms |

조회 후 관리 힙은 약 1.68MB, 프로세스 Working Set은 약 92.6MB였습니다. WPF 화면의 ViewModel·컨트롤·가상화 캐시는 포함하지 않으며, 하드웨어와 데이터 내용에 따라 결과가 달라집니다.

2026-10-14 리팩토링 검증에서는 macOS / .NET 10.0.12에서 파일·구조화 항목 각각 10,000개, 구조화 20컬럼으로 실행했습니다. 구조화 기본 경로 오름차순 첫 500행은 20.7ms, offset 9,500의 500행은 17.0ms였고, 내림차순은 각각 10.4ms와 17.7ms였습니다. 숫자 정렬 첫 500행은 36.5ms, 조건 7개를 동시에 적용한 첫 500행은 16.2ms였습니다. 위 100,000행 기록과 데이터 크기가 다르므로 개선율 비교에 사용하지 않습니다. 경로 정렬에 임시 정렬이 생기지 않는지는 오름차순·내림차순 실제 SQL의 `EXPLAIN QUERY PLAN` 회귀 테스트로도 검증합니다.

2026-10-16 검증에서는 macOS 27.0.1 / Arm64 / .NET 10.0.12, HEAD `a9db137`에 미커밋 정렬 페이지 개선을 적용한 상태에서 파일·구조화 각각 10,000개 / 20컬럼으로 실행했습니다. 숫자 역순 첫 500행은 순서 준비를 포함해 34.2ms, 마지막 500행은 10.5ms였고 20개 분산 페이지는 합계 225.8ms였습니다. 날짜·텍스트 정렬의 마지막 페이지는 각각 11.8ms와 8.7ms였습니다. 전체 10,000행 숫자순 내보내기 순회는 264.3ms였으며 누락 없이 10,000행을 확인했습니다. 원본 합성 DB는 `/private/tmp/fe-ordered-perf.xnzKiW`에 남겼습니다. 동일 커밋의 Windows UI나 이전 버전과의 통제된 A/B 측정이 아니므로 프레임 반응성 또는 개선율을 보장하는 수치가 아닙니다.
